# План: реконект, стабильность соединения и исправление игровых эффектов

Дата: 2026-09-09. База ревью: `2450a93`, ветка `main`.

Этот документ — инструкция для агента-исполнителя. Подробные задачи, зависимости и проверки находятся в [TASKS.md](TASKS.md). Создание этих документов не означает, что изменения уже реализованы.

## Цель

После обрыва соединения, обновления страницы или временной задержки два игрока возвращаются в тот же матч, получают согласованное состояние мира и интерфейса и продолжают с текущего этапа без зависания или потери выбора улучшений.

Приоритет: реконект и согласованность состояния; затем исправление боевых эффектов. Не расширять задачу до переработки игры.

## Согласованные требования и границы

| Область | Требование |
| --- | --- |
| Debug | Доступен всем участникам. Не добавлять права администратора, авторизацию debug или отключение в production. |
| Чрезмерные debug-команды | Ограничить случайно огромные операции и валидировать числа, сохранив обычные возможности отладки. |
| Движение | Не вводить строгую серверную модель движения ради защиты от читов. |
| Реконект | Сохранять матч, пока серверный процесс работает и хранит комнату в памяти. |
| Восстановление слота | Автоматически восстанавливать своего персонажа по токену. Не занимать чужой отключённый слот без токена. |
| Ожидание | Двухминутный срок начинается при отключении. Бой ждёт обоих участников. |
| Луч босса | Один удар на 40 базового урона одному игроку от одного луча за одну активацию. |
| Щит босса | Восстанавливается многократно через 60 секунд игрового времени после уничтожения последнего пилона. Это стимулирует быстрее убить босса. |
| Улучшения | Исправить фактическую длительность метки, оглушение в соло и периодику яда. |
| Публикация | Не деплоить и не обновлять размещённый сервер в рамках плана. |

Не входят в задачу: сохранение матча после перезапуска процесса, новая база данных, вход с другого устройства без токена, замена отсутствующего участника новым человеком, античит, общий редизайн интерфейса или баланса.

### Рабочие решения из обсуждения

Следующие детали предложены в плане как правила реализации. Основные числа и поведение луча/щита согласованы пользователем; перечисленные детали не следует описывать как отдельно подтверждённые им решения:

- Сопротивление уменьшает базовые 40 урона луча. Специальная неуязвимость после воскрешения и во время рывка сохраняется.
- Заблокированный защитой удар не помечает игрока уже поражённым: если защита закончилась до конца активации, попадание ещё возможно.
- Разные лучи считаются разными атаками и могут нанести по 40 каждый. Обычная краткая защита после попадания не должна случайно отменять другой луч. Не менять глобально правила остальных источников урона.
- Сохраняются существующие условия первого щита, двухсекундное оглушение при его разрушении и запрет сочетания щита с турельным режимом. Если 60 секунд истекли во время турели, восстановить щит при первом допустимом выходе без нового полного отсчёта.
- После восстановления связи и устранения остальных причин остановки выполнить один трёхсекундный отсчёт.
- Частота полной страхующей синхронизации и пределы debug-операций выбираются исполнителем по измерениям и обычным сценариям отладки.

## Подготовка

1. Прочитать актуальные инструкции репозитория, проверить текущий коммит и `git status`.
2. Сохранить локальные изменения пользователя. Если версия ушла от `2450a93`, заново найти указанные функции: номера строк в TASKS.md — ориентиры исходного ревью.
3. Проверить зависимости и штатную сборку. При необходимости установить их по lock-файлу без произвольного обновления версий.
4. Зафиксировать исходный результат тестов и воспроизведения проблем.

Исходная проверка ревью: `npm run test:full` — 387 тестов пройдено; `npm run test:live` — успешный матч двух настоящих WebSocket-клиентов, четыре проверки пройдены. Эти результаты не заменяют проверку текущей версии.

## Этапы реализации

| Этап | Задачи | Результат и условие перехода |
| --- | --- | --- |
| 0. База | T00 | Известны состояние репозитория, исходные тесты и воспроизведения. |
| 1. Идентичность | T01 | Участник имеет стабильный ID, сокет заменяется без переноса всей игровой личности. Старое соединение не управляет новым. |
| 2. Реконект | T02–T04 | Токен живёт весь матч; ожидание обоих, паузы и текущий выбор корректно восстанавливаются. |
| 3. Синхронизация | T05–T06 | Пропуск сообщений не оставляет клиента с неверными данными; два реальных клиента выдерживают сценарии реконекта. |
| 4. Боевая логика | T07–T10 | Луч — один удар на 40; щит повторяется; длительности и яд работают в бою. |
| 5. Debug | T11 | Debug открыт всем, но одна ошибочная команда не запускает неограниченную работу. |
| 6. Приёмка | T12 | Регрессии, сборка, реальная сеть и доступная браузерная проверка завершены; подготовлен отчёт. |

T07–T11 можно реализовывать независимо от основного переноса идентичности, но сетевые проверки попаданий, пауз и эффектов должны быть повторно выполнены после интеграции. Зависимости не означают требование запускать отдельных агентов.

## Архитектурные ориентиры

### Стабильный участник и текущее соединение

Игровые ссылки используют постоянный ID участника внутри матча. `socket.id` — только транспорт. При реконекте привязка меняется атомарно. Проверить все ссылки: пули, эффекты, цели врагов, ожидающие выборы, адресные сообщения, роль хоста, определение локального персонажа на клиенте.

Оба пути входа/восстановления используют общую логику. Проверка токена должна предшествовать смене привязки и другим изменениям комнаты.

### Несколько независимых причин паузы

Отсутствие участника, синхронизация, ручная пауза, выбор улучшения, отсчёт продолжения и завершение матча не должны отменять друг друга. Бой продолжается только при отсутствии блокирующих причин. Просроченный ввод не воспроизводится после реконекта. Debug-команды остаются явным способом менять состояние при остановленном бое.

### Восстановление мира и интерфейса

Клиент получает полный актуальный мир и текущую фазу взаимодействия. При выборе улучшения возвращаются существующие карточки, `offerId`, факт уже принятого выбора и остаток перебросов. Перезагрузка не создаёт новые предложения и не применяет улучшение повторно.

### Надёжное состояние и частые координаты

Пропуск старых координат допустим. Описания сущностей и изменения характеристик должны восстанавливаться надёжно. Исключить глобальный однократный `staticSent` как гарантию доставки. Использовать идентификатор запуска матча и порядок снимков; добавить полные снимки при восстановлении и периодическую страховку. Запросы восстановления неизвестных сущностей ограничить по частоте.

## Проверки

Подробная матрица — в TASKS.md. Обязательны:

- Поведенческие регрессии, использующие реальные игровые функции, а не только проверяющие значения `stats`.
- Два настоящих Socket.IO/WebSocket-клиента для реконекта, подтверждения снимков и переносов соединения.
- Проверка интерфейса после обновления страницы в браузере, если инструмент доступен; недоступность указать в отчёте, не выдавая VM-моки за браузерную проверку.
- Пропуск первого описания врага и сообщения с изменением характеристик.
- Разные шаги симуляции для лучей и таймеров; паузы не расходуют игровые таймеры.
- `npm run test:full`, `npm run test:live`, проверка логов и размеров/частоты сообщений.

Добавлять тесты по мере исправления соответствующей проблемы. После успешной интеграционной проверки не повторять тяжёлые прогоны без новых изменений или выявленных рисков.

## Определение готовности

Задача завершена, когда оба игрока могут восстановить тот же матч после всех обязательных сетевых сценариев, их мир и интерфейс согласованы, улучшения не теряются и не дублируются, боевые исправления проходят поведенческие проверки, debug доступен обоим и нет непроверенных регрессий, блокирующих обычную игру.
